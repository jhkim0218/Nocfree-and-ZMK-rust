# 동글 ↔ Bluetooth 1 ↔ Bluetooth 2 전환 지연 분석과 개선안

작성일: 2026-09-12. 분석 기준: NocFree-and-rust KR 버전, `bf84d37`의 현재 소스.

사용자의 피드백은 “동글·블루투스·블루투스2 사이를 오갈 때 연결이 오래 걸리고 불안정하다”이다. 사용자는 보유한 NocFree-and-rust KR 펌웨어에서의 피드백임을 확인했다. UF2의 정확한 해시, 운영체제, 지연 시간, 재현 로그는 아직 없으므로 아래 내용은 현재 Rust KR 설정의 코드 분석이다. 연결 전환 경로는 배열 간 공통이며 KR 매핑만의 문제라는 증거는 없다. 펌웨어 수정·이미지 빌드·플래시는 수행하지 않았다.

## 결론

단순히 전파가 약해서 생기는 문제로 단정할 수 없다. 현재 구현에는 **전환 요청 처리 지연**, **빠른 연속 조작의 요청 유실**, **비선택 호스트의 재접속 경쟁**, **입력 준비 상태와 오류 처리 부족**이라는 구체적인 위험 요인이 있다. 먼저 요청 처리와 연결 준비 과정을 고치고, 그다음 광고 주기를 조정하는 순서가 적절하다.

동글도 내부적으로 BLE를 사용한다. 왼쪽은 오른쪽 키보드용 central 연결 하나와 동글/PC용 peripheral 연결 하나를 사용한다(`src/platform.rs:36`, `:43`). 동글과 PC를 동시에 연결해 두는 구조가 아니므로, 정상 전환에도 기존 연결 해제 → 광고 → 새 연결 → 보안 → 입력 준비가 필요하다. 이 구조 자체가 결함은 아니지만 즉시 전환에는 한계가 있다.

## 원인 후보와 근거

### 1. 보안 대기 중 다음 전환 요청을 처리하지 못함 — 우선순위 높음

- `src/bin/central.rs:650`의 `wait_for_security()`는 20ms × 250회, 약 5초까지 기다린다.
- 동글과 PC 연결 양쪽에서 이 함수를 직접 await한다(`:736`, `:795`). 이 구간에는 `BLE_CONTROL.wait()`와의 경쟁 대기가 없다.
- 보안 완료 전 연결이 끊겨도 루프에서 연결 해제 여부를 확인하지 않는다. 보안 미완료 상태라면 남은 대기를 소모할 수 있다.
- 따라서 연결 도중 다른 모드/프로필로 바꾸면, 이전 연결 절차가 끝날 때까지 새 요청이 지연될 수 있다. 정상 연결마다 반드시 5초가 걸린다는 뜻은 아니다.
- `disconnect_ble()`도 해제 요청 오류를 무시하고 핸들이 사라질 때까지 기다리며 애플리케이션 차원의 기한이 없다(`:643`). 실제 무한 대기 발생은 미확인이다.

**개선:** 보안 대기를 전환 요청·연결 해제와 함께 기다리고, 새 요청이 오면 이전 시도를 정리한다. 연결 해제 오류를 기록하고 유한한 복구 정책을 둔다. 시간 초과만으로 활성 연결이 남은 상태에서 다음 광고를 시작해서는 안 된다. 보안 수준이나 본딩 검증을 낮추지 않는다.

### 2. 전환 알림이 프로필 선택 명령을 덮어쓸 수 있음 — 코드상 확인된 위험

- `BLE_CONTROL`은 큐가 아니라 한 슬롯 `Signal<BleControl>`이다(`src/bin/central.rs:101`).
- 여기에 `Select`, `Pair`, `Clear` 같은 명령과 `OutputChanged` 알림을 함께 넣는다(`:89`, `:163`, `:171`, `:204`).
- 소비자가 보안/해제 처리를 기다리는 동안 `Select(1)` 다음 `OutputChanged`가 들어오면 선택 명령이 덮어써진다. `BONDS.select()`는 소비 시점에 실행되므로 선택 자체가 반영되지 않을 수 있다.
- 반면 `Select(1)` → `Select(2)`를 마지막 선택으로 합치는 것은 자연스럽다. 문제는 서로 다른 의미의 메시지를 한 슬롯에 섞었다는 점이다.
- 근거: 설치된 embassy-sync 0.7.2의 `src/signal.rs`와 [Embassy Signal 공식 설명](https://docs.embassy.dev/embassy-sync/0.7.0/default/signal/struct.Signal.html). 공식 문서 예시는 0.7.0이며, 설치 버전에서도 덮어쓰기 구현을 확인했다.

**개선:** 선택할 출력/프로필은 최신 희망 상태로 유지하고 Signal은 깨우는 용도로 사용한다. 실제 연결에 적용하는 프로필과 희망 프로필을 구분해, 이전 연결의 보안 콜백이 새 프로필 본딩을 건드리지 않도록 한다. 본딩 삭제·페어링은 유실되면 안 되는 명령이므로 별도로 보존한다. 단순히 모든 명령을 무제한 큐에 넣으면 이미 지나간 모드로 차례로 연결하는 부작용이 있다.

### 3. 비선택 PC도 일단 연결할 수 있음 — 경쟁 발생은 실기 검증 필요

- PC 쪽은 100ms 주기의 비지향 광고를 사용하며 별도 연결 필터를 지정하지 않는다(`src/bin/central.rs:775`).
- 선택한 프로필의 상대인지 확인하는 시점은 연결이 성립한 뒤다(`:795`, `src/bond_store.rs:124`).
- 따라서 이전 PC가 자동 재접속하면 연결 후 거절·해제를 반복할 가능성이 있다. 동시 활성 호스트 수와 OS 재접속 동작에 따라 지연 편차가 생길 수 있다.
- 프로필 변경 시 이름은 바꾸지만(`:632`) 이 경로에서 프로필별 로컬 BLE identity를 설정하지는 않는다. 이름 변경만으로 기기 identity 분리가 된다고 보아서는 안 된다.

**개선:** 이미 본딩한 프로필은 선택 상대에 대한 연결 허용 목록 또는 지향 광고를 검토한다. 신규 페어링 때는 검색 가능 광고를 유지한다. 상대의 privacy 주소/IRK 처리와 SoftDevice 전역 목록이 오른쪽 split 검색에 미치는 영향을 확인해야 한다. 연결 허용 목록의 역할은 [Nordic 연결 과정 문서](https://academy.nordicsemi.com/courses/bluetooth-low-energy-fundamentals/lessons/lesson-3-bluetooth-le-connections/topic/connection-process/?version=v3.3.0)를 참고한다. 동일 PC의 여러 프로필 사용 문제가 확인될 때만 identity 분리와 기존 본딩 마이그레이션을 별도 설계한다.

### 4. 같은 프로필을 다시 눌러도 재접속함 — 불필요한 지연

연결된 상태에서 현재와 같은 `Select`가 들어와도 먼저 disconnect한 뒤 select한다(`src/bin/central.rs:805`). `BondStore::select()` 역시 변경 여부를 확인하지 않고 저장을 요청한다(`src/bond_store.rs:87`).

**개선:** 같은 프로필이고 정상 입력 가능한 상태라면 짧은 선택은 아무 일도 하지 않도록 한다. 페어링 진입·연결 복구 요청은 별도로 처리한다. 연결이 느려서 사용자가 단축키를 다시 누르는 행동이 재연결을 반복시키지 않게 한다.

### 5. 연결 성공과 HID 입력 가능 상태가 구분되지 않음 — 첫 입력 유실 후보

- `send_ble_notification()`은 Resources/Busy만 5ms 후 재시도하고, 그 밖의 Raw 오류는 `true`를 반환한다(`src/bin/central.rs:609`). 성공하지 않은 전송이 성공으로 취급된다.
- PC 출력은 보안/속성 복원 후 시작하지만, HID 특성별 알림 구독 준비를 명시적으로 확인하지 않는다. `BleHidServerEvent`는 동글 구독만 구별한다(`src/ble_hid.rs`).
- PC의 GATT 쓰기마다 상태를 재동기화하므로 나중에 복구될 여지는 있다(`src/bin/central.rs:806`). 그러나 첫 입력 성공을 보장하는 구조는 아니다.

**개선:** 알림 미준비와 영구 오류를 구별하고 오류를 기록한다. 저장된 구독 복원 또는 새 구독을 확인한 뒤 최신 절대 입력 상태를 동기화한다. 사용하지 않는 consumer/pointer 특성의 미구독이 keyboard 출력을 막지 않도록 특성별로 처리한다. 오래된 타이핑을 나중에 몰아서 재생하지 않는다.

### 6. 동글의 검색 공백이 큼 — 동글 복귀 지연의 직접 후보

`src/bin/dongle.rs:121`은 기본 ScanConfig를 사용한다. 설치된 `vendor/nrf-softdevice/src/ble/central.rs:301`의 기본값은 interval 2732, window 500이며 단위는 625µs다. 즉 약 1.7075초 주기 중 312.5ms만 검색하는 설정으로, 명목상 약 1.395초의 검색 공백이 있다. 동글 광고가 20ms여도 수신기가 검색하지 않는 동안에는 발견할 수 없다. 실제 지연은 위상·무선 스케줄링·간섭에 따라 달라지며 이 숫자는 전체 재접속 시간의 상한이 아니다.

**개선:** USB 전원을 사용하는 동글의 연결 대기 scan window를 interval에 가깝게 넓히는 방안을 먼저 비교 측정한다. 동글은 키보드의 모드 전환 시점을 직접 알지 못하므로 “전환 직후”만 적용하려면 별도 신호 없이 가능한 연결 해제 후 고속 검색 또는 대기 중 검색 정책으로 정의해야 한다. 오른쪽 split 검색 설정까지 일괄 변경하지 않는다.

### 7. 추가 최적화 후보 — 주요 원인으로 단정하지 않음

- PC 광고는 100ms, 동글 광고는 20ms다(`src/bin/central.rs:775`, `:715`). PC 재연결 초기에 한정해 20~30ms 광고를 시험하고 이후 저전력 주기로 복귀할 수 있다. 광고를 5배 빠르게 해도 전체 연결이 5배 빨라지지는 않는다.
- 동글은 매번 서비스 탐색과 CCCD 쓰기를 한다(`src/bin/dongle.rs:157`). 이는 정상 초기화 비용이다. 지연을 계측하기 전에 핸들 캐시와 펌웨어 변경 시 무효화 체계를 추가하지 않는다.
- 동글의 보안 대기도 최대 약 5초이며 연결 해제 검사가 없다(`src/bin/dongle.rs:82`). 양쪽을 함께 개선해야 빠른 왕복 전환 때 이전 시도 대기를 줄일 수 있다.
- 동글 supervision timeout은 4초다(`src/dongle_protocol.rs:9`). 정상적인 명시적 연결 해제에 매번 붙는 대기 시간이 아니다. 신호 소실 상황과 구분해 측정하고 우선적으로 줄이지 않는다.
- 동글 모드에서 짧은 Fn+1/2/3 선택은 무시된다(`src/bin/central.rs:204`). 이 상태에서 미리 BLE2를 선택했다고 생각하면 기대와 실제 목적지가 달라질 수 있다. 현 동작을 재현 절차에 명시하고, 선택 예약 지원은 제품 동작 변경으로 별도 결정한다.
- PC GATT 쓰기마다 sys attrs 캡처·저장을 요청하고 저장 작업은 페이지를 지운 뒤 쓴다(`src/bin/central.rs:807`, `src/bond_store.rs:140`, `:558`). 저장 내용이 같으면 생략하고 변경분을 합치는 개선이 가능하다. 실제 연결 지연 기여도는 측정 전에는 알 수 없다.

## 권장 구현 순서

1. **관측 확보:** 전환 요청, 이전 연결 해제, 광고 시작, 연결 성립, 상대 거절, 보안 완료/실패, 구독 준비, 첫 HID 전송 시각과 오류를 기록한다. 키 값과 보안 키는 기록하지 않는다.
2. **전환의 정확성:** 요청 유실 방지, 보안 대기의 취소/연결 해제 감지, 동일 프로필 무동작을 적용한다. 기존 연결 콜백이 끝나기 전에 적용 프로필을 바꾸지 않는다.
3. **입력 안정성:** 준비 상태·알림 오류를 처리하고 전환 전 release와 재연결 후 최신 상태 동기화를 검증한다. BLE 프로필 전환은 출력 모드가 같아 router의 모드 release와 별도로 확인해야 한다.
4. **재접속 속도:** 동글 scan window 확대, 비선택 상대 연결 차단, 전환 직후 빠른 광고를 각각 측정한다. split 재연결과 배터리 회귀를 확인한다.

동시 다중 호스트 연결은 초기 개선 범위에서 제외한다. 연결 수·메모리·전력·라우팅 구조까지 바꾸므로 위 문제를 먼저 해결한 뒤에도 요구 성능에 못 미칠 때 검토한다.

## 구현 완료 사항

2026-09-12에 다음 공통 연결 경로를 구현했다. 레이아웃별 키맵이 아닌 `central`과 `dongle` 바이너리를 수정했으므로 ANSI·ISO·JIS·KR에 동일하게 적용된다.

- 출력 모드 변경 알림을 프로필 명령과 별도 Signal로 분리했다. 이제 물리 동글/USB/BLE 전환이 프로필 선택·페어링·삭제 명령을 덮어쓰지 않는다.
- 동글/호스트 보안 대기에서 연결 해제를 즉시 감지하고, 호스트 출력 전환·프로필 전환이 들어오면 최대 5초 보안 대기를 취소해 새 목적지를 처리한다.
- 이미 연결된 프로필을 다시 선택하면 연결을 끊지 않으며, 선택 값이 실제로 달라질 때만 선택 프로필을 flash에 저장한다.
- 기계식 출력 스위치 안정화 시간을 20ms에서 50ms로 늘렸다.
- PC BLE 광고 주기를 100ms에서 20ms로 줄였고, USB 동글은 scan window를 scan interval과 같게 해 검색 공백을 없앴다. 이 변경은 동글 USB 전력과 키보드의 BLE 대기 전력 사이의 트레이드오프가 있다.
- `Resources`/`Busy` 알림 오류는 최대 200ms만 재시도하고, 다른 Raw 오류를 성공으로 취급하지 않는다. 동글 출력 전환 때는 release report 다음에 최신 pressed 상태를 전송한다.

비선택 PC를 연결 전에 차단하는 accept-list/directed 광고, 동글 GATT handle 캐시, 다중 호스트 동시 연결은 구현하지 않았다. 각 항목은 privacy·본딩 호환성과 메모리/전력 동작을 별도 실기로 확인해야 한다.

## 검증 계획과 합격 기준

실행 전 성공 기준은 다음과 같이 둔다. 수치는 현재 성능의 보장이 아니라 개선 작업의 제안 목표다.

- 본딩된 동글·PC1·PC2가 모두 깨어 있는 조건에서 6방향 전환을 각각 30회 측정한다.
- 측정 시작은 물리 모드 확정 또는 프로필 선택 명령 발생, 끝은 대상 PC가 첫 HID 입력을 수신한 시각이다. 연결 완료 표시만으로 끝내지 않는다.
- 각 방향별 중앙값·p95·최댓값·실패 횟수를 기록한다. 초기 목표는 p95 2초 이내, 5초 초과 및 잘못된 대상 입력 0회이며 OS별 결과를 분리한다.
- 연결/보안 중 100~300ms 간격으로 다른 모드와 프로필을 선택해 최종 목적지에 도달하는지 확인한다. 마지막 선택 유실, 이전 시도 때문에 남는 5초 대기가 없어야 한다.
- 같은 프로필 재선택 시 정상 연결이 끊기지 않아야 한다.
- Ctrl/Shift/일반 키를 누른 채 전환하고 놓았을 때 이전·새 PC 모두 키가 눌린 상태로 남지 않아야 한다. 오른쪽 입력도 함께 확인한다.
- 대상 PC가 꺼짐/절전인 경우의 기다림은 정상 조건 지연과 분리한다. 기다리는 중 다른 사용 가능한 대상으로 바꾸면 반응해야 한다.

## 이번 분석에서 수행한 검증과 한계

- `python -B tools/build_release.py --all-layouts --dongle`: ANSI·ISO·JIS·KR host tests, host/ARM clippy (`-D warnings`), ARM Left/Right/Dongle 빌드, UF2/DFU 생성, Python firmware 검사를 통과했다. ANSI는 104개, ISO/JIS/KR은 각각 111개 라이브러리 테스트가 통과했다.
