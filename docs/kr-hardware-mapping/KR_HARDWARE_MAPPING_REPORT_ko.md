# NocFree & KR 실물 스캔 매핑 확인 결과

## 문서 목적

NocFree & KR 실물에서 확인한 키 입력 문제의 원인과 PCA9555 전기 매핑을 공유한다. 이 문서는 구현 방법이나 코드 변경안을 제안하지 않고, 실물에서 관측한 사실만 정리한다.

- 확인일: 2026-08-28~29
- 대상: NocFree & KR 왼쪽·오른쪽 키보드 한 세트
- 범위: 키 스캔 입력과 물리 키 순서
- 제외: bootloader, SoftDevice, 보호 flash, UICR, 동글

KR은 아직 Experimental 배열이므로 다른 생산 시기나 PCB revision에서도 동일한지 추가 확인이 필요하다.

## 관측된 문제

### 왼쪽

- `H`, `Y`가 입력되지 않았다.
- `asdfgh` 행과 `zxcvb` 행이 오른쪽으로 밀려 입력됐다.
- `Cmd`가 `Y`, `Space`가 `H`로 입력되는 등 하단 키까지 밀렸다.

### 오른쪽

- 물리 키 `67890-=`가 `7890-Backspace`처럼 입력됐다.
- 기능키 열이 `F6`이 아니라 `F7`부터 시작했다.
- `Home`, `Delete`가 숫자 `6`으로 입력됐다.
- 하단 보조키와 Fn 위치도 밀렸다.

macOS/Windows 모드를 바꾸거나 저장 키맵만 초기화해서는 이 문제가 해결되지 않았다.

## 확인 방법

전기 위치를 추측하지 않고 다음과 같이 측정했다.

1. 네 PCA9555 주소 `0x20`, `0x22`, `0x24`, `0x21`의 설정 성공 여부와 포트 읽기 여부를 확인했다.
2. 디코딩 전의 네 16비트 입력값을 눌림 순간에 기록하는 진단 펌웨어를 사용했다.
3. 오른쪽 물리 키 50개를 각 행에서 왼쪽부터 오른쪽 순서로 눌렀다.
4. 각 눌림에서 high→low로 바뀐 주소·포트·비트를 기록했다.
5. 왼쪽은 문제가 있던 키와 하단 행을 포함해 raw 순서를 확인했다.

## 원인

### 왼쪽

왼쪽 KR 실물은 `0x21`의 추가 키를 사용하지 않았다. 기존 가정과 달리 `Y`, `H`를 포함한 39개 키가 `0x20`, `0x22`, `0x24`의 여섯 표준 포트에 배치되어 있었다.

- `Y`: `0x22 P0.6`
- `H`: `0x22 P1.6`
- `0x21 P0.0`은 왼쪽 키 입력이 아니었다.

추가 포트에 있다고 가정한 키 때문에 `Y/H`가 누락되고 그 이후 raw 순서가 밀렸다.

### 오른쪽

오른쪽은 두 전기 입력이 서로 잘못 대체되어 있었다.

- 실물에 없는 키로 포함된 입력: `0x24 P1.7`
- 실제 키인데 제외된 입력: `0x21 P0.3`

이 때문에 첫 기능키, 숫자 `6`, `Home/Delete`, 하단 키가 visual 위치와 다른 raw 동작을 사용했다.

## 확인된 왼쪽 매핑

왼쪽은 세 PCA9555의 여섯 표준 포트만 사용한다.

| 물리 스캔 행 | 전기 입력 수 | local raw 범위 |
|---|---:|---:|
| `0x20 P0` | 7 | `0~6` |
| `0x20 P1` | 7 | `7~13` |
| `0x22 P0` | 7 | `14~20` |
| `0x22 P1` | 7 | `21~27` |
| `0x24 P0` | 6 | `28~33` |
| `0x24 P1` | 5 | `34~38` |

- 행별 키 수: `[7, 7, 7, 7, 6, 5]`
- 전체 키 수: `39`
- `0x21` 추가 키 수: `0`
- `Y`: local raw `20`
- `H`: local raw `27`
- 하단 다섯 키: local raw `34,35,36,37,38`

## 확인된 오른쪽 매핑

오른쪽 전체 50키를 물리 행의 왼쪽→오른쪽 순서로 측정한 결과다.

| 물리 행 | 키 수 | 왼쪽→오른쪽 전기 입력 |
|---|---:|---|
| 1행 | 10 | `0x20 P0.0~P0.7`, `0x21 P0.0`, `0x21 P0.1` |
| 2행 | 9 | `0x20 P1.0~P1.7`, `0x21 P0.2` |
| 3행 | 9 | `0x22 P0.0~P0.7`, `0x21 P0.3` |
| 4행 | 7 | `0x22 P1.0~P1.6` |
| 5행 | 8 | `0x24 P0.0~P0.7` |
| 6행 | 7 | `0x24 P1.0~P1.6` |

오른쪽 local raw는 표준 포트를 먼저 연속 배치하고 `0x21 P0.0~P0.3`을 마지막 네 값으로 배치하면 다음과 같다.

- 표준 포트 행별 키 수: `[8, 8, 8, 7, 8, 7]`
- 표준 포트 local raw: `0~45`
- `0x21 P0.0~P0.3`: local raw `46~49`
- 전체 키 수: `50`

전체 키보드에서 왼쪽 39키 뒤에 오른쪽 local raw를 붙였을 때, 물리 행별 global raw 순서는 다음과 같다.

- 1행: `39,40,41,42,43,44,45,46,85,86`
- 2행: `47,48,49,50,51,52,53,54,87`
- 3행: `55,56,57,58,59,60,61,62,88`
- 4행: `63,64,65,66,67,68,69`
- 5행: `70,71,72,73,74,75,76,77`
- 6행: `78,79,80,81,82,83,84`

## 실물 재확인 결과

확인된 전기 순서를 적용한 시험 펌웨어에서 다음 결과를 확인했다.

- 왼쪽 `asdfghzxcvb`: 정상 입력
- 오른쪽 `67890-=`: 정상 입력
- 오른쪽 `Home`: 커서 이동
- 오른쪽 `Delete`: 실제 문자 삭제
- 양쪽 backlight: 점등
- 오른쪽 확장기 주소 마스크: `0x0F`
- 오른쪽 입력 포트 마스크: `0x7F`
- 왼쪽 확장기 주소 마스크: `0x07`
- 왼쪽 입력 포트 마스크: 완전 전원 재시작 후 `0x3E → 0x3F`

## 별도 관측 사항

왼쪽 펌웨어 적용 직후 한 차례 확장기 설정은 성공했지만 첫 입력 읽기가 시작되지 않아 오른쪽 키만 입력되는 상태가 있었다. 왼쪽 USB 분리, 전원 OFF, 5초 대기, 전원 ON, USB 재연결 후 여섯 입력 포트가 모두 읽히고 왼쪽 입력이 복구됐다.

이는 매핑 자체와 별개로 초기 I2C 입력 읽기 또는 전원 시작 조건을 추가 점검할 필요가 있음을 의미한다.

## 추가 확인이 필요한 항목

- 다른 KR 실물 또는 PCB revision에서 동일 매핑인지 확인
- 오른쪽 `F6~F12` 전 키의 OS 이벤트 확인
- 양쪽 하단 modifier와 Right Fn 조합 확인
- Bluetooth, 2.4G, sleep/wake 이후 양쪽 입력 확인
